# Design decisions

- **Hook `pg.Client.prototype.query`, not a query builder.** Every library on `pg` sends its statements there, pools' clients included, so one hook covers Drizzle, Kysely and plain `pg` without adapters.
- **Read the locks from the SQL text and the answer, without asking the server.** Row locks don't show in `pg_locks` until someone waits on them, and an extra query inside the app's transaction would change what it does. The answer's fields carry each column's table and position, which names the rows a statement locked when it returns their primary keys.
- **Name a lock by its table or its advisory purpose, as lockdep names a lock by its class.** Tests give each path its own rows; naming locks by row would never let two paths meet.
- **Keep the call sites on each edge, and capture them once a statement is answered.** A query builder's thenable is called from a microtask, so a stack taken as the statement is sent stops at the builder. Taken in the answer's continuation, it runs back through the `await`s to the app.
- **Find a cycle as a ring of two or three edges whose modes conflict at every step.** PostgreSQL's conflict tables decide, so share against share never fails. Two-lock cycles are the common inversion and three-lock rings the next; each is found from every edge with a fixed amount of work, while a search for rings of any length can enumerate exponentially many. Two paths of a ring that held one guard they can't hold at once rule it out, since they can't run together.
- **Rule a cycle out only by a guard on the same row or key.** Matching a guard by table would hide real deadlocks between paths that each lock a different row of it first. The cost is that per-tenant guards seen in different tests don't count.
- **When it can't tell, don't fail, and list it.** Rows a statement doesn't name are taken to be ones the transaction holds, or all of the table's for the rest of it, and the statement is listed as keys unknown, since a silent guess can hide a real cycle as easily as a false one; the locks of one statement get no edges between them, since the plan, not the text, orders them. A false failure costs more trust than a missed path.
- **Record an insert's foreign-key checks from the catalog.** A check holds the parent's row for `KEY SHARE`, which waits for a `FOR UPDATE` or a delete of it: a path that holds a parent row first and a path that inserts its child first are a real inversion. Only an insert's are counted, and only when it wrote every row it gave: an update checks a key only when its value changes, which its statement doesn't say, and a counted check that never ran would be a false failure.
- **Count a statement that answered no row as a lock.** One that waited for a row a concurrent writer changed, and then found it no longer matching, keeps the lock (PostgreSQL's EvalPlanQual re-check), and the same statement locks rows whenever it matches some, so its place in its path's order is real. Its rows are those its `where` names, or unknown. An advisory call runs once per answered row, so a statement that answered none took no advisory lock.
- **Fail the Vitest run from the global teardown.** Test files run in their own workers, so each leaves its edges in a folder the global setup opened, through Vitest's `provide`/`inject`; the teardown sees them all and throws.
